# Деплой subpolare

Локальный репозиторий: `/Users/subpolare/Desktop/Personal/subpolare`.
GitHub: `git@github.com:subpolare/subpolare.blog.git` (на серверах допустим HTTPS этого же репозитория).

| Назначение | SSH | Каталог | Production Compose | Сайт |
|---|---|---|---|---|
| Источник публикаций, RU | `ssh blog` | `/srv/subpolare.blog/` | `docker-compose.production.yml` | `https://subpolare.ru/` |
| Зарубежное зеркало, COM | `ssh netcup` | `/srv/subpolare.blog/` | `docker-compose.mirror.yml` | `https://subpolare.com/` |

Compose-проект на обоих серверах — `subpolareblog`; перед изменениями сверь labels работающих контейнеров. Pepic расположен в `/srv/pepic` на обоих серверах. Устройство каналов и проверки описаны в `etc/mirror-operations.md`.

Запрос деплоя разрешает эту последовательность без повторного подтверждения. По умолчанию обновляй оба сервера до одного SHA. Если пользователь явно ограничил запрос одним сервером, соблюдай ограничение и сообщи о расхождении версий. Запрос редактирования скилла сам по себе не разрешает деплой.

## Границы действий

- Локально разрешены чтение, проверки, `git add -A`, commit всех изменений этого репозитория и push. Включай существующие изменения пользователя, удаления и новые неигнорируемые файлы. Не делай исправлений кода в рамках отдельного запроса только на деплой.
- Удалённо разрешены `git pull --ff-only`, необходимые операции Docker именно этого проекта, описанный ниже помощник миграций COM и сверка медиа штатным обработчиком. Чтение других файлов/логов разрешено, если требуется диагностике. Не выводи секреты или полные env-файлы.
- Не изменяй вручную удалённые файлы, SSH, nginx хоста, права, секреты или пакеты; не управляй чужими контейнерами, не удаляй тома и не выполняй глобальную очистку Docker. Не используй `reset`, `clean`, force push и автоматический rollback.
- Каждый удалённый сеанс с изменениями начинай с `cd /srv/subpolare.blog && test "$(pwd -P)" = /srv/subpolare.blog && ...`. При несовпадении пути прекращай команду. Не обходи ограничения через симлинки, mounts, Docker или скрипты.
- Разовое разрешение root SSH при первоначальной настройке netcup **не действует для будущих деплоев**. Работай как `subpolare`.
- Начальная настройка репликации, выдача прав, создание subscriptions, смена ключей, ручные SQL/backfill и восстановление из backup не являются обычным деплоем. При необходимости такого действия сообщи препятствие; текущая ошибка не расширяет разрешения.

## Проверки перед публикацией

1. Прочитай `AGENTS.md`, проверь local status, staged/unstaged diff, новые файлы, ветку и upstream. Remote должен вести в указанный GitHub. Не переключай ветку автоматически.
2. Проверь отсутствие секретов во всех публикуемых изменениях. Не добавляй игнорируемые `.env`, `secrets`, `runtime`, `pgdata`, сертификаты. Если безопасно опубликовать все изменения нельзя — остановись, не исключай часть молча.
3. Выполни `git diff --check` и проверки по `AGENTS.md`. Backend: `poetry run python3 manage.py test --settings=subpolare.test_settings`. Изменения persistence/репликации проверяй отдельно на временном PostgreSQL; production для тестовых записей не использовать. Изменения редактора: `node --test frontend/tests/post-editor.test.cjs` и `node --check frontend/static/js/post-editor.js`. При провале обязательных проверок остановись до публикации. Если локальное окружение неисправно, допустим эквивалентный изолированный контейнер с тем же кодом/lock-файлом; укажи это в отчёте.
4. Read-only проверь оба удалённых checkout: реальный путь, remote, ветку/upstream, чистоту дерева, HEAD и labels Compose. При конфликте, посторонних изменениях или неясном upstream остановись. Ветки должны соответствовать одному назначению push/pull.
5. Локально выполни `git add -A`, проверь staged diff, создай краткий commit и сделай обычный `git push`. Без изменений не создавай пустой commit; при наличии опубликуй непереданные commits. Запомни полный SHA. При ошибке push не переходи к деплою.

## Обновление серверов

1. Повторно проверь чистоту и ветки, затем выполни `git pull --ff-only` в каждом checkout. HEAD обоих серверов должен точно совпасть с опубликованным SHA. При несовпадении или ошибке не запускай Docker.
2. Прочитай актуальные production Compose, Dockerfile, Makefile и изменённые миграции. Не используй dev Compose. Не пересоздавай PostgreSQL, Pepic и SSH-туннель для обычного изменения приложения.
3. Собери образ `blog_app` на COM и RU с проверенным `-p subpolareblog` и соответствующим Compose. Сборка обоих образов должна завершиться до обновления приложений. Не используй `down`.
4. При новых совместимых добавляющих миграциях сначала на COM выполни `python3 utils/mirror-db-owner.py migrate --noinput`. Помощник читает существующий секрет владельца, не выводит его и допускает только явные операции. Он не должен использоваться для первичной настройки subscription при обычном деплое. Несовместимая миграция требует отдельного согласованного порядка; остановись и объясни конфликт.
5. На RU обнови `blog_app blog_previews blog_maintenance blog_media_sync` через `docker compose -p subpolareblog -f docker-compose.production.yml up -d --no-deps ...`. Старт RU выполняет migrations; не запускай их повторно. Проверяй успешный старт до продолжения.
6. На COM обнови `blog_app blog_maintenance` через `docker compose -p subpolareblog -f docker-compose.mirror.yml up -d --no-deps ...`. Приложение COM работает с ограниченной ролью и не запускает migrations при старте.
7. После успешного обновления запусти явную сверку файлов на RU: `docker compose -p subpolareblog -f docker-compose.production.yml exec -T blog_media_sync python3 manage.py mirror_media_sync --once`. Штатный ключ позволяет только передачу в `/srv/pepic` на COM без удаления; не подменяй его административным ключом. Изменения статей/карты/реакций передаются постоянно через PostgreSQL, а файлы — после событий и с периодическим повтором.
8. Если diff меняет COM nginx, проверь конфигурацию через сервис `nginx` и перезагрузи только его после успешной проверки. Не меняй Nginx хоста RU в рамках обычного деплоя.
9. При ошибке сборки, миграций или старта прекращай дальнейшие изменения; используй read-only диагностику. Не повторяй команды вслепую и не откатывай автоматически.

## Проверка результата

- Сверь SHA, состояние обновлённых контейнеров, образ, время старта и рестарты. Читай ограниченные логи (`--since 10m --tail 150`) нужных сервисов; не публикуй секреты из логов.
- Проверь TLS без `-k`, `/_mirror/health` обоих сайтов, главную и конкретную существующую статью. Для принудительного просмотра нужного зеркала используй cookie `mirror=ru` или `mirror=com`, поскольку геопереход может менять домен.
- Проверь выдачу местных изображений COM, свежесть `.mirror-synced`, отсутствие ошибок `blog_media_sync`/`ru_tunnel`, состояние `pg_stat_subscription` на COM и `pg_replication_slots` на RU. Только read-only SQL для этих проверок, без строк подключения с секретами.
- Для изменений поведения выбери конкретные проверки по diff. Production не использовать для создания тестовых статей, загрузок или реакций. Недоступные для безопасной проверки сценарии явно укажи вместе с результатами изолированных тестов.
- Если сервис запускается, допустимы ограниченные read-only повторы до двух минут. Не объявляй успех только по завершению Docker-команды.
- Итог: commit/ветка, push/pull обоих серверов, обновлённые сервисы, доступность обоих сайтов, состояние синхронизации, выполненные проверки и оставшиеся ограничения.
